## Overview

The Analyze Endpoint allows you to process documents in order to analyze the content of the document, to extract information and to enrich the document with additional insights.

Document analysis is performed by an asynchronous job triggered by the user providing configuration and input data. The final result can be fetched when the job finished, but intermediate results can be accessed as soon as they're available.

With the Analyze Endpoint you can

- create a job to process input data

- specify a task that need to be performed

- and pass configuration options to control the jobs behavior

Finally you can retrieve the job's output when the job finished.

## Concepts

### Job

A job represents a collection of tasks that is performed asynchronously. Every job can be uniquely identified by a generated identifier.

The lifecycle of a job is defined by the following states:

<div>

|            |                                                     |
|------------|-----------------------------------------------------|
| Status     | Description                                         |
| ACCEPTED   | The job got accepted, but is not yet scheduled.     |
| PENDING    | The job is scheduled and ready for being processed. |
| INPROGRESS | Job execution is in progress.                       |
| DONE       | Execution is done and was successful.               |
| FAILED     | Execution failed.                                   |
| CANCELLED  | Execution was cancelled.                            |

</div>

Every job runs with a given priority. The following priorities exists:

<div>

|  |  |
|----|----|
| Priority | Description |
| LOW | Low priority jobs are scheduled for execution after all DEFAULT priority and URGENT priority jobs are done. |
| DEFAULT | Default priority jobs are scheduled for execution after all URGENT priority jobs are done, but before any LOW priority job is scheduled. |
| URGENT | Urgent priority jobs are scheduled for execution before any DEFAULT priority or LOW priority jobs. |

</div>

### Entity

Any input or output data is named Entity. An entity can be binary data like a PDF or an image or it can be an object represented by an JSON structure or it can be a primitive value like a Number or a media type.

The list of supported entities can be retrieved by the `meta/entity` endpoint.

Entities of a job can be retrieved by the `{jobId}/entity/{name}` endpoint.

Examples are:

<div>

|  |  |  |
|----|----|----|
| Entity name | Type | Description |
| Sofa | Binary (application/octet-stream) | The **S**ubject **of** **A**nalysis. This is the most generic input entity that can be used for data analysis. Use this entity if you don't know the meaning of the data in order to let the Analyze API determine the meaning by itself. |
| Sofa.ContentType | Mediatype | The media type of the Subject of Analysis. This entity can be used to tell the Analyze API the already known media type, or you can let the Analyze API determine the media type and get the result back as an output. |
| Document.Type | List of Strings | Specifies the types of the document. E.g. whether the document is an Invoice or not. |
| Document.SearchablePdf | Binary (application/pdf) | This is the document in PDF with searchable text layer. |

</div>

Every entity has a unique name, a scope and a value of a specific type.

The scope of an entity is either

- PROVIDED as input for the job

- GENERATED by the job

### Task

A task represents a unit of work to be performed by the job. A task is bound to an entity that needs to be produced. E.g. the task `Document.Type` tells the job to generate the entity `Document.Type`.

The job automatically derives more tasks that need to be done in order to be able to perform the requested task. If, for example, the user would like to get the Document.Type of the SofA, the job first needs to compute Sofa.ContentType and then based on the detected media type the job might run OCR first in order to have the required input entities for document type detection.

The list of supported tasks can be retrieved by the `meta/task` endpoint.

Examples are:

<div>

|  |  |
|----|----|
| Task name | Description |
| Sofa.ContentType | Detect the media type of `Sofa` input. The result will be available as `Sofa.ContentType` entity. |
| Document.Type | Detect the document type of `Sofa` input. The result will be available as `Document.Type` entity. |

</div>

## Using the Analyze API Endpoint

The Analyze Endpoint can be used to submit documents for asynchronous analysis. Analysis work is represented by a job. In order to analyze a document do the following steps:

1.  Submit a new job, passing input data, configuration options, priority and tasks in a single request

2.  Wait for job to finish

3.  <span class="inline-comment-marker" ref="16c49bbc-47bd-47ac-bf28-5355dbbefbbe">Fetch results</span>

4.  Delete job

## Most common client mistakes

### Rate limit exceeded

To ensure consistent availability and performance we apply some limits to how the API can be used.

The Analyze API does not accept an unlimitted number of job requests. Quotas exists for

<div>

|  |  |
|----|----|
| **Quota** |  |
| Job Submission | Limits the number of registered analysis jobs (e.g. 10’000) |
| Urgent jobs | Limits the number of urgent analysis jobs (e.g. 2’000) |

</div>

The remaining quotas are reported in every API response and in case the limit is reached.

### Too many parallel requests

To ensure consistent availability and performance we apply some limits to how the API can be used.

Sending concurrent requests can be a key part of a strategy to maximize throughput, but it is important to keep it under control. A high number of concurrent threads is something your application can use to have a significant improvement in performance, but only if the individual operations are relatively quick and the transfered data is small.

Submitting jobs and retrieving final job results are heavy operations. You need to keep the number of parallel requests low in order to achieve high network throughput.

### Waiting for job to finish

Document processing can take a long time. So does OCR for example take ~2 seconds per page.

If you don’t take advantage of the asynchronous architecture of the Analyze API, you’re client will be idle the most time, waiting for the results to become available.


![[2530751376-uc-sequential.png]]



Just increasing the number of parallel clients will make the situation worse, because you might run into the decreasing network throughput by too many parallel heavy operations.

The solution is to let a single client manage multiple job in parallel.


![[2530751376-uc-batches.png]]



In the above scenario, the client has no idle (waiting) time.

Let’s assume the following execution times:

- job submission takes 200ms

- document processing takes 3s

- fetching the results takes 200ms

- deleting the job takes 50ms

The basic sequential scenario takes ~50 seconds for 15 documents.

The managed sequential scenario takes ~6 seconds for 15 documents.

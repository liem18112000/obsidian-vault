# Performance Issue: Slow Document Listing Query in MongoDB - "eArchive" page

> [!info] Imported from Confluence
> Space **LUZ** · updated 2025-11-14 · [open original](https://axonivy.atlassian.net/wiki/spaces/LUZ/pages/48869834837/Performance+Issue+Slow+Document+Listing+Query+in+MongoDB+-+eArchive+page)
> Relevance 0.714 · topic `infra`

## **1. Overview**

When accessing the **eArchive** GUI, the web client needs to retrieve a paginated list of documents (48 per page).  
The query must return:

- All stored documents, **or**

- Documents archived into folders, **or**

- User-uploaded documents that do not belong to any folder.

The results must be **sorted by the user's latest activity** (latest change/view).

As the total number of documents grows, this query becomes significantly slower, causing the GUI page to take an excessively long time to load.

## **4. Identified Performance Bottlenecks**

### **4.1 Regex on** `origin` **Field**

The following condition uses a case-insensitive regex:

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="94809279-cc88-4f08-8a7d-f1d85868cef8" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
{ "origin": { "$regex": "^User uploaded$", "$options": "i" } }
```

</div>

</div>

This can be simplified to a direct equality comparison:

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="10e2ae5b-cc4a-4c66-810e-5c87a4c3309d" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
{ "origin": "User uploaded" }
```

</div>

</div>

This reduces computation and allows MongoDB to make better use of indexes (if available).

------------------------------------------------------------------------

### **4.2 Sorting on a Non-Indexed Field**

The most expensive operation is:

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="12354cfd-ecb1-44e6-9497-5ac68bc9c89b" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
{ "$sort": { "_updatedDate": -1 } }
```

</div>

</div>

Because:

- Sorting happens **after** the `$lookup`, making it sort a much larger dataset.

- The field `_updatedDate` **does not have an index**, causing a full collection scan and in-memory sort.

- With a large number of documents, this becomes extremely slow.

This is the primary cause of the slow response time.

------------------------------------------------------------------------

## **5. Proposed Solution**

### **5.1 Add Index for Faster Sorting**

Create an index on the `_updatedDate` field:

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="b1dc9e24-972f-4ced-9863-11019b883861" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
db.documents.createIndex({ "_updatedDate": -1 })
```

</div>

</div>

This allows MongoDB to perform the sort using the index instead of scanning the entire collection.

------------------------------------------------------------------------

### **5.2 Move** `$sort` **Immediately After** `$match`

Reposition the sort stage to before `$lookup`:

**Before (current):**

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="cd3cc6df-8753-4ade-b278-cf203a01b351" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
$lookup → $sort → $skip → $limit
```

</div>

</div>

**After (optimized):**

<div class="code panel pdl conf-macro output-block" hasbody="true" macro-id="7f80b2f8-07fe-4c6f-89bd-82c45dc38e21" macro-name="code" style="border-width: 1px;">

<div class="codeContent panelContent pdl">

``` syntaxhighlighter-pre
$match → $sort → $lookup -> $skip → $limit
```

</div>

</div>

Sorting earlier:

- Reduces the number of documents entering `$lookup`

- Minimizes unnecessary computation

- Significantly improves performance, especially with paging

------------------------------------------------------------------------

## **6. Summary**

<div>

|  |  |  |
|----|----|----|
| Issue | Impact | Fix |
| Regex match on `origin` | Slower matching, prevents index usage | Use direct equality check |
| `_updatedDate` not indexed | Full collection scan and slow sort | Add index on `_updatedDate` |
| Sort placed at end of pipeline | Sorts a large post-lookup dataset | Move `$sort` right after `$match` |

</div>

With these optimizations, the document search operation becomes significantly faster, ensuring the eArchive GUI loads quickly even for tenants with very large document sets.

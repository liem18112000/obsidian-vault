# ~/.claude mixes config, runtime state, and credentials in one tree

Claude Code keeps everything under one `~/.claude` root with no separation between the three things living there: **durable config** you would want to version (`CLAUDE.md`, `settings.json`, `agents/`, `hooks/`, `skills/`), **regenerated runtime state** (`hooks/state/`, `plugin-state/`, caches, logs, poller offsets), and **live credentials** (`.credentials.json`, `hooks/telegram/telegram-notify.config`). So "back up my Claude setup" is never a plain copy — it is a filter, and getting the filter wrong publishes secrets.

Non-obvious places credentials hide, beyond the ones with obvious names:

- **`settings.local.json`** — approved `Bash(...)` permission entries are stored **verbatim**, so a one-time `curl -H "Authorization: Bearer eyJ..."` that you approved is now a bearer token living permanently in your config. This is the surprising one: the permission allowlist is a credential store nobody thinks of as one.
- **Skill scripts with dev defaults** — a `$DefaultPassword = "..."` or a generated `.env` heredoc with `CLIENT_SECRET=` reads as harmless "it is only dev" until the skill is in a repo.
- **Machine-local markers** that are not secret but break on another machine: `skills/_context` (one word, the active env), `luz-kubernetes-root.config` (an absolute repo path), `plugins/installed_plugins.json` (install paths + SHAs).

Two practical consequences:

1. Scan for `eyJ[A-Za-z0-9_-]{20,}` before publishing, but expect false positives — `eyJ` is just base64 for `{"`, so any embedded JSON blob matches. Confirm a real JWT by its three dot-separated segments.
2. Filter at **copy** time, not with `.gitignore`. A secret excluded by `.gitignore` never entered the tree; a secret committed and then gitignored is still in history. Ship the `.gitignore` too, but as defence for the *next* re-sync.
